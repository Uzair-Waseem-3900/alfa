# Architecture rules

These are enforced constraints for ANY backend work in this project, not
just performance-review passes — read this file before writing or editing
any model/selector/service/serializer/view, every time (see `CLAUDE.md`).
Every rule below exists because it was found broken in a real app during
the 2026-08 review and had to be fixed after the fact; the point of writing
it down is that a new feature should get it right the first time.

- **O(1) reads.** Dashboard/report/all-time stats read a stored field off a singleton (`CashFlow`/`TaxFlow`/`AssetFlow`/etc.), never a live `Sum()`/`Count()` over history. Live aggregation only OK when genuinely bounded (month-count trend queries, live snapshot reports like Inventory Valuation). No stored source for a needed number → flag to user, don't silently ship O(n).
- **DRY.** Generalize before duplicating — one `BaseReportPrintView`/template serves all reports, not one per report. Exception: genuinely unique documents (invoice, PO) get their own template. Prefer existing public selectors/services (`get_asset_stats()`, etc.) over reimplementing loops or reaching into internals.
- **App shape, every time**: `models.py`, `permissions.py` (`IsAdminOrSuperuser`, admin/superuser-only), `selectors.py` (all reads), `services.py` (all writes, `@transaction.atomic`), `serializers.py`, `views.py` (thin, **generics-based only** — no hand-rolled logic that a generic view already covers), `urls.py`, `admin.py`, `backfill_<app>` command. Never read/write directly in views — go through selectors/services.
- **Soft delete always.** Never hard-delete a row that has any historical/audit relevance — use an `is_deleted` flag (or equivalent) and filter it out everywhere, mirroring existing models.
- **Pagination always.** Any endpoint whose output is a list gets pagination — use the project's global default `pagination_class`, never `None` and never a custom override.
- **Indexed search always, via `search_q()` only.** ALL text search/filtering goes through `backend.search.search_q(term, *fields)` — never write `icontains` (or any text-match lookup) directly in app code; `backend/search.py` is the single place the lookup lives. Every column `search_q` targets MUST be backed by a pg_trgm GIN expression index — `USING gin (upper(<col>) gin_trgm_ops)` — created in a vendor-guarded migration (`if schema_editor.connection.vendor != "postgresql": return`, so SQLite dev is a no-op; pattern: `purchases/migrations/0010_product_trigram_search_indexes.py`). A plain `db_index`/B-tree CANNOT serve a `%term%` match and is not a substitute. Never ship an unindexed search on a growing table.
- **Never filter a DateTimeField with `__date`.** `field__date=`/`__date__gte`/`__date__lte` on a `DateTimeField` defeats any B-tree index on that column (forces a per-row cast, full scan) even when the column is indexed — this was the single most-repeated finding across the whole performance review (cash_flow, billing, purchases, ledger, profits, reports, ...). Always filter with a half-open range instead: `field__gte=<local midnight of start>`, `field__lt=<local midnight of the day AFTER end>`. Reuse `purchases.selectors._day_start`/`_next_day_start` (aware datetimes at local midnight) rather than reinventing them — `reports.selectors._apply_datetime_range_filter` is the fullest worked example (single `date` / `date_from`/`date_to` range, both). A plain `DateField` (e.g. `expense_date`, `payment_date`) needs no such treatment — filter it directly.
- **Never call `.date()`/`.year`/`.month`/`.strftime()` directly on `timezone.now()` (or any stdlib `datetime.now()`/`datetime.today()`/`date.today()`) — always go through `timezone.localtime(...)` first.** This project's real users are in Pakistan (`TIME_ZONE = "Asia/Karachi"`), but the backend runs on Render (Singapore) and the DB on Supabase (Singapore) — server geography doesn't matter, `USE_TZ=True` means every `DateTimeField` is stored as a UTC instant regardless of where the process runs, and `timezone.now()` returns that instant. Extracting a calendar date/month/year from it WITHOUT `.localtime()` first silently reads the UTC calendar day, not the Pakistan one — wrong for roughly 5 hours a day (UTC 19:00–23:59 = midnight–5am PKT), every single day, not an edge case. Found and fixed repeatedly across a full-codebase sweep: `purchases.services.next_reference`'s year, `purchases.services.mark_lost_inventory_found`'s `recovered_at`, `profits.services._earliest_period`'s year/month, `ledger.management.commands.backfill_ledger`'s year. `timezone.now()` used as a plain timestamp assigned straight to a DateTimeField (`created_at=timezone.now()`, `deleted_at=timezone.now()`) is correct as-is and needs no change — this rule is specifically about extracting a calendar date/period FROM it. Prefer `timezone.localdate()` (Django's built-in shorthand for `timezone.localtime(timezone.now()).date()`) where only the date is needed. Mirrors the identical frontend bug class (`new Date().toISOString()` instead of local getters, see `instructions/frontend.md`) — same mistake, same fix shape, both ends.
- **Index the exact date/timestamp column a selector filters or orders by.** `AuditMixin`'s default `created_at` is deliberately unindexed for models nothing sorts/filters by (e.g. `Category`, `Shelf`, `Supplier`) — but the moment ANY selector adds `.order_by("-created_at")`/a date filter on it, or a new report starts filtering by some other date column (`confirmed_at`, `accepted_at`, `assigned_at`, ...), override that field with `db_index=True` in the same change. Missing this was found repeatedly (`PurchaseOrder`/`PurchaseReturn`/`LostInventoryRecord.created_at`, `RecurringExpenseAssignment.assigned_at`, `BackupHistory.created_at`) — don't ship a new report/list ordering against an unindexed column.
- **Catch-up sweeps must be O(1) per request, not O(rows) per request.** A "catch-up on read" mechanism (no cron — see below) that loops every row on every read (e.g. re-checking every investor's/asset's latest posted period) is fine at first but becomes an unnecessary per-request cost once there's real data — the sweep only actually needs to run once, at the first read after a new period starts. Gate it with a `<thing>_caught_up_through = "YYYY-MM"` marker field on the relevant Flow singleton: compare to the current period (free — the singleton is already being read) and skip the per-row loop entirely when it matches; only run the real sweep, then stamp the marker, when it's stale. Any user action that makes old postings incomplete (e.g. editing a growth/depreciation rate) MUST reset the marker to `""` in the same service call, so the very next read re-sweeps with the new rate — never wait until the marker naturally expires. Pattern: `cash_management.CashManagementFlow.growth_caught_up_through` / `assets.AssetFlow.depreciation_caught_up_through`.
- **Guard monthly/periodic auto-posting with a real uniqueness constraint.** Any "post one row per (thing, period)" catch-up (investor growth, asset depreciation, monthly profit finalization) MUST have a DB-level `UniqueConstraint` on `(thing, period)` (or `period` alone for a singleton-per-period model) — two near-simultaneous reads at a period boundary can otherwise both pass a `.filter(...).first()` check and both post, double-counting that period forever. Wrap the create in `with transaction.atomic():` (a savepoint) and catch `IntegrityError` — treat it as "another request already posted this period," `refresh_from_db()` and return, don't raise. Never let this surface as an unhandled 500.
- **`.filter()` on a prefetched relation silently discards the prefetch.** If a selector does `Prefetch("a__b", queryset=...)` (or a bare `prefetch_related`) and the serializer's `to_representation` then calls `instance.b.filter(...)` to re-narrow it, Django throws the cached prefetch away and re-queries — a hidden N+1 that query-count tests will catch but casual review won't. Bake every filter/ordering the serializer needs INTO the `Prefetch`'s queryset at the selector layer, and have the serializer read the relation as-is (no further `.filter()`/`.exclude()` in `to_representation`).
- **STRICT: every list/detail endpoint must run in well under 200ms server-side against the real production database (Supabase/any remote Postgres), not just "fast" on local SQLite.** Local SQLite has near-zero per-query latency, so an N+1 that fires 25 extra queries costs a few milliseconds locally and is invisible in dev — the SAME N+1 against a real network-hosted Postgres costs roughly 100ms PER QUERY (measured, not estimated: `aws-*.pooler.supabase.com` from this project's own dev machine), so 25 extra queries is ~2.5 seconds of pure network round-trip time, and 50 extra queries is ~5 seconds. "It feels fine when I test it" is not verification — count the actual queries (`django.db.connection.queries` with `DEBUG=True`, or a `CaptureQueriesContext` test) before calling any endpoint done. A paginated list endpoint (25 rows) has no excuse to run more than a small, fixed number of queries (typically 2–4: count + page + at most one or two prefetches) — if it's more than that, it's an N+1, not "the database being slow."
- **STRICT: a serializer's relations have a blast radius — changing one serializer can silently break a DIFFERENT selector in a different app.** This already happened once: adding `credit_score`/`credit_tier` fields to `CustomerReadSerializer` was itself done correctly (the selector that builds `CustomerReadSerializer` directly was updated with a matching `select_related`) — but `InvoiceReadSerializer` in `billing/serializers.py` separately NESTS `CustomerReadSerializer` as its `customer` field, and `billing/selectors.py`'s `_invoice_qs()` was never updated to also `select_related("customer__credit_score")`. Result: the invoice list page silently gained a 25-query N+1 that nobody wrote directly — it was inherited through nesting. **The rule: whenever you add a field to a serializer that requires a new relation (FK, reverse FK, OneToOne), grep every place that serializer is used — both views that serialize it directly AND every other serializer that nests it — and add the matching `select_related`/`prefetch_related` to every queryset that feeds ANY of them, not just the one you're directly editing.** Don't consider the change done until you've traced the full nesting graph.
- **Convert a check-then-act uniqueness/protection violation into a clean 400, don't let it crash.** Any `if Model.objects.filter(...).exists(): raise ValidationError(...)` immediately followed by `.create()` has a race window where the DB's own constraint (`UniqueConstraint`, `on_delete=PROTECT`) fires instead — wrap the create/delete in a savepoint, catch `IntegrityError`/`ProtectedError`, and re-raise the SAME `ValidationError` the pre-check would have given. The success path is untouched; only the crash-on-race path becomes a normal 400.
- **A multi-source "recent activity"/breakdown view that will grow with history needs an event table, not a live merge.** Building a drill-down/audit view by querying N source models and merging+sorting the results in Python (however clean at first) becomes O(all history) per page load the moment any one source table gets large. If a new feature needs to show "everything that happened across N models, newest first," design the event table from day one — don't ship the Python-merge version and defer the fix. `cash_flow.CashMovement` is the reference implementation; see the "Cash movements are events" rule below for the concrete checklist.
- **Chunk batch deletes/updates over an unbounded set — never one giant `pk__in`/`exclude(pk__in=...)` query.** A prune/sync/cleanup job that computes "everything not in this set" and issues one DELETE with a huge parameter list works fine in dev and gets slow/memory-heavy once a table reaches real production size. Read the target IDs in chunks (`.iterator(chunk_size=...)`), diff in Python, delete in bounded batches (pattern: `backups.services._prune_remote_model`).
- **Sequential reference numbers need a `DocumentCounter` row, not a text-sorted `MAX()`/count scan.** Never generate `PREFIX-YYYY-####` by sorting/counting existing rows — that's O(n) per generation, races under concurrent creates, silently collides after 9999, and breaks across soft-delete-filtered managers. Use a `(doc_type, year)`-keyed counter row locked with `select_for_update()` inside the same atomic block (pattern: `purchases.services.next_reference`, reused by billing).
- **Cash movements are events.** The cash-in-hand drawer reads ONLY the `cash_flow.CashMovement` event table (one indexed query), never a Python merge over source tables. Any service that moves `cash_in_hand` MUST pair its `sync_*` call with `record_cash_movement(source)` / `reverse_cash_movement(source)` / `refresh_cash_movement(source)` in the SAME transaction — see `instructions/cash-in-hand.md` for the full five-place checklist (builder map, backfill command, oracle selector).
- Frontend mirrors backend shape: `services/<app>Api.js`, `hooks/use<App>.js`, `pages/<app>/`, nav section in `Layout.jsx`, routes in `App.jsx`.
- Rate/% inputs: user types whole numbers (`15`), frontend converts to/from the stored fraction.
- **Snapshot at lock-in.** Historical figures (`share_percent_snapshot`, `name_snapshot`, `rate_applied`) are stored at the moment they're true, never re-derived from current state later.
- **Earnings ≠ capital.** A profit payout never touches capital fields (`net_stake`, `total_invested`, `total_withdrawn`). Reinvestment = two separate, independently-reversible ledger entries (payout out, real transaction in), not one combined record.
- **Catch-up mechanisms** (no cron/celery — "catch-up on view" pattern) must be registered in `GET /api/system/catch-up/` (`backend/backend/views.py`), in dependency order (currently assets → investors → profits).
- **Disclaimer banner** on any computed-but-uncertified financial page (business worth, monthly profit, payouts, tax) — copy wording from `BusinessWorthPage.jsx`/`TaxesPage.jsx`.
